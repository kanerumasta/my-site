Hi,

You describe an application to an AI.

It creates the pages, connects a database, adds an API, fixes its own errors, and gives you something that works.

That experience can make software design patterns feel like artifacts from another era.

Why learn about Factory, Strategy, Adapter, or Observer when AI can write the code for you?

[![Colorful software design pattern blocks fitting into a modular puzzle](https://www.macibale.site/images/design-patterns-puzzle-hero.png)](https://www.macibale.site/blog/do-design-patterns-still-matter-when-ai-writes-the-code?utm_source=buttondown&utm_medium=email&utm_campaign=design_patterns_and_ai)

Here is the distinction I keep coming back to:

> **Vibe coding changes who types the code. It does not change what the code must survive.**

The first version asks, “Can this work?”

Software design asks, “What happens when this needs to change?”

That question matters when a weekend experiment becomes a product, starts storing private information, accepts payments, or gains users who depend on it.

Design patterns are not pieces of code we need to memorize. They are names for problems developers repeatedly encounter:

* **Factory:** Who should create the thing we need?
* **Strategy:** Which behavior should we use here?
* **Adapter:** How do two incompatible systems communicate?
* **Observer:** Who needs to know that something happened?

AI can generate any of these patterns in seconds. The harder judgment is knowing whether the pattern solves a real problem—or merely makes a small application look impressively complicated.

My new article explores why that judgment still matters, gives a quick introduction to four patterns, and explains why recognizing the problem is becoming more valuable than memorizing the implementation.
